# Game Rules — Authoritative Source

This file is the single source of truth for gameplay behaviour. Implementation must not invent conflicting mechanics. Numeric values may be tuned later through accepted changes.

## Core rule

The deterministic simulation engine selects actions and outcomes. AI may only generate natural-language expression for already-decided actions.

## Numeric scale

Unless stated otherwise, traits and relationship values use integer values from 0 to 100 inclusive.

## Determinism

- Every simulation run receives a stored random seed.
- The same persisted state, rule version, and seed must produce the same decisions.
- Text generated by an external AI provider need not be byte-identical, but it cannot alter mechanics.

## Character traits

Initial traits:

- Humour
- Confidence
- Empathy
- Aggression
- Curiosity
- Honesty
- Sociability
- Ambition
- Patience
- Romantic openness

Traits change rarely and only through explicit life events.

## Mood

Mood has:

- type
- intensity
- start time
- expected decay
- source event

Mood influences action likelihood and tone, but does not override eligibility rules.

## Character activity

Activity likelihood is based on:

- configured activity level
- world time and schedule
- mood intensity
- active goals
- relevant events
- recent action count
- fatigue/repetition penalty

A character must not flood the feed. Per-run and per-day limits are configurable world settings.

## Social actions

### Like

A like decision may consider:

- opinion alignment
- relationship affinity
- author familiarity
- topic interest
- post quality score
- current mood

### Reply

A reply additionally requires sufficient relevance or emotional motivation. The engine decides stance, tone, target, and intent before AI wording.

### Follow

Follow requires repeated positive interactions, topic interest, or influence. Unfollow requires sustained negative relevance, conflict, or disinterest; one minor event is insufficient.

## Relationship model

Relationships are directional. A trusting relationship from A to B does not imply the same value from B to A.

Values:

- Trust
- Familiarity
- Respect
- Affection
- Comfort
- Attraction
- Commitment
- Rivalry
- Jealousy

All changes:

- are clamped to 0–100
- require a source event
- record a reason
- are idempotent by source event and rule

Example default impacts:

- Helpful private reply: Trust +2, Comfort +2
- Public defence: Trust +7, Respect +5, Affection +3
- Sincere compliment: Affection +2, Comfort +1
- Public insult: Trust -8, Respect -5, Rivalry +6
- Broken promise: Trust -12, Comfort -6
- Repeated neglect: Affection -2 per qualified event, capped per period

These are initial balancing values, not UI promises.

## Derived non-romantic states

- Stranger: Familiarity < 15
- Acquaintance: Familiarity >= 15
- Friend: Familiarity >= 40, Trust >= 40, Affection >= 35
- Close Friend: Familiarity >= 65, Trust >= 65, Affection >= 60
- Rival: Rivalry >= 60 and Respect may remain positive
- Enemy: Rivalry >= 75, Trust <= 20, Affection <= 20

State derivation must consider active romantic status first.

## Memory

Memory types:

- PersonalFact
- Promise
- Secret
- Compliment
- Insult
- Conflict
- SharedExperience
- RomanticEvent
- Achievement
- Loss
- OpinionStatement

Memory fields include importance, emotional value, confidence, source, created time, optional expiry, and last recall time.

Recall score uses:

- importance
- recency
- emotional magnitude
- subject match
- topic match
- relationship relevance
- recall repetition penalty

Only a limited number of relevant memories are passed to AI.

## Private messages

- The player and one character have at most one active direct conversation per world.
- Reply eligibility is rule-based.
- Reply delay depends on schedule, mood, relationship, urgency, and sleep/work state.
- Important messages may create memories.
- Sending a message does not guarantee a reply.

## Dating eligibility

Initial eligibility requires:

- Familiarity >= 55
- Attraction >= 60
- Trust >= 45
- Comfort >= 40
- No incompatible active romantic status
- No recent severe unresolved conflict
- Character romantic openness and preferences permit it

Invitation acceptance score may consider:

- Attraction
- Trust
- Comfort
- Compatibility
- Mood
- confidence
- recent positive/negative events
- character goals

The engine decides acceptance or rejection before dialogue is generated.

## Romantic state machine

Allowed main path:

```text
None -> Interested -> Dating -> Committed -> Engaged -> Married
```

Alternative transitions:

```text
Interested -> Rejected
Dating/Committed/Engaged/Married -> Separated
Dating/Committed/Engaged -> BrokenUp
Married/Separated -> Divorced
BrokenUp/Separated -> Reconciled -> previous valid active state
```

Every transition requires:

- eligibility validation
- source event
- timestamp
- reason codes
- relationship timeline entry

Impossible transitions must be rejected.

## Breakup evaluation

Breakup pressure may increase from:

- low trust
- unresolved repeated conflicts
- low commitment
- sustained neglect
- incompatible goals
- severe broken promise
- jealousy combined with evidence-based events

A single random roll cannot end a healthy relationship without sufficient accumulated pressure.

## Trends

Trend score uses:

- recent post count
- unique actors
- replies
- reposts
- engagement velocity
- influential actor participation
- world-event relevance
- repetition decay

## World simulation

A simulation run:

1. Acquires idempotency protection for a world/time interval.
2. Advances world time.
3. Selects active characters.
4. Produces decisions.
5. Executes rule-only actions.
6. Queues text-generation work.
7. Persists results.
8. Updates relationships, memories, and trends.
9. Creates notifications.
10. Records run result and seed.

## Catch-up simulation

Catch-up compresses elapsed time. It must not execute every missed minute.

It calculates:

- elapsed world time
- expected activity volume
- major events
- selected visible posts/messages
- aggregate follower/reputation effects
- relationship changes with supporting events
- summary items

Catch-up must be bounded by configurable maximum work per request.
